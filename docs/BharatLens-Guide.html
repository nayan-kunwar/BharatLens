1. Project Overview

What BharatLens Does

BharatLens answers one core question:

"Something happened in the world. What does it mean for India?"

It is NOT a news aggregator. It is a geopolitical intelligence platform that:

  • Ingests news from global sources (RSS feeds)
  • Extracts factual claims and evidence
  • Classifies events by India-relevant impact categories
  • Generates structured impact assessments with source attribution
  • Maintains audit trails for AI-generated analysis
  • Supports human review before publication

Core Product Loop

WORLD EVENT | v WHAT HAPPENED? (Fact extraction from sources) | v WHY DID IT HAPPEN? (Context and claims) | v WHY DOES INDIA CARE? (India relevance analysis) | v WHAT IN INDIA IS EXPOSED? (Exposure assessment) | v WHAT COULD HAPPEN? (Scenario analysis) | v WHAT SHOULD WE WATCH NEXT? (Monitoring signals)

Failure Modes

FailureEffect
Postgres down/ready returns 503; /health still 200; public reads fail
Redis down/ready returns 503; background jobs pause; public reads still work
Worker crashAPI and web still run; no new ingest/analysis
API crashWeb homepage shows "unreachable"; worker still processes
LLM unavailableAnalysis jobs fail; existing published data unaffected

Key Design Decisions

  • Modular Monolith first: One process per service, clear module boundaries, no premature microservices
  • Evidence-first: Claims backed by sources, not just LLM output
  • Human-in-the-loop: AI generates drafts; humans review and publish
  • Append-only history: Impact assessments are versioned; corrections create new versions
  • Separate evidence_strength from analysis_confidence: Never collapse into one number

Event Status Lifecycle

CANDIDATE (auto-grouped from unmatched coverage) | v DRAFT (being prepared) | v ANALYZED (AI analysis complete) | v REVIEW_REQUIRED (waiting for human review) | v PUBLISHED (visible to public) | v UPDATED (new assessment published) | v ARCHIVED (no longer active)

Key Constraints

  • events.slug unique - public URLs
  • articles.url unique - ingest URL deduplication
  • articles (source_id, external_id) unique - RSS GUID per source
  • claims (event_id, statement) unique - idempotent extraction
  • evidence (claim_id, url) unique - one URL per claim
  • impact_assessments (event_id, version) unique - append-only versions
  • Circular FK: assessments reference events; events reference the current assessment (ON DELETE SET NULL)

8. Data Ingestion Pipeline

Pipeline Flow

Feed Config (bbc-world, un-news) | v Fetch RSS/Atom (HTTP with timeout + User-Agent) | v Parse Items (title, link, guid, date, description) | v Normalize (canonical URL, collapsed title, stripped HTML) | v SHA-256 Content Hash (title + day + summary) | v Deduplication |-- Hard: unique URL / (source, external_id) |-- Soft: content hash, exact title, token overlap | v Insert Article (status: NORMALIZED) | v Record ingestion_jobs row | v Candidate Event Discovery (if new articles cluster)

What Is Stored

BharatLens does NOT scrape full articles. It stores only metadata:
  • Source metadata (publisher name, URL)
  • Article title
  • Canonical URL
  • Optional short summary (max 500 characters)
  • Publication time
  • Content hash (SHA-256)

News Source Adapter

interface NewsSourceAdapter {
  fetchArticles(): Promise<RawArticle[]>;
}

Currently ships one adapter: RssAdapter. A future News API adapter can implement the same interface.

9. Deduplication Strategy

Multi-Layer Approach

LayerMethodMatch TypeWindow
1URLHard (no second row)None
2External ID (RSS GUID)Hard (no second row)None
3Content hashSoft (status=DUPLICATE)None
4Exact normalized titleSoft (status=DUPLICATE)48 hours
5Token overlapSoft (status=DUPLICATE)48 hours

Why Not Semantic Embeddings?

  • Volume is tiny - PostgreSQL unique constraints are sufficient
  • Embeddings require a vector database (premature)
  • False positives from embeddings are harder to debug
  • Token overlap + gazetteer entity is precise enough for this scale
  • False negatives are accepted until evidence shows they matter

Candidate Event Discovery

After ingest inserts new articles, the worker scans unmatched coverage and clusters it with the precision dedupe matcher inside a 48-hour window. Clusters that pass three gates become CANDIDATE events:

  1. At least 2 articles
  2. A shared gazetteer entity (country, organization name)
  3. A deterministic India-relevance token

10. Claims & Evidence System

Claim Types

TypeMeaningSource
FACTDirectly supported by reliable evidenceHuman reviewer only
ANALYSISReasoned interpretation based on factsExtractor or model
SCENARIOA possible future outcomeExtractor or model
UNKNOWNInsufficient reliable informationExtractor or model
Key Rule: RSS headline extraction and model-generated claims are NEVER typed FACT. FACT stays a reviewer/seed decision only.

Evidence Strength Computation

evidence_strength is computed from linked evidence rows:

  • Count distinct source_id values -> sourceCount / independentSourceCount
  • Count distinct sources with type GOVERNMENT or INTERNATIONAL_ORG -> officialSourceCount
  • Classification: WEAK (1 source) / MODERATE (2-3) / STRONG (4+)

An LLM percentage is never stored. evidenceReason restates the counts in natural language.

Claims Extractor (Deterministic)

Published event | v Find articles sharing gazetteer entity + 2 tokens with event | v Attach article to event (event_articles) | v If article overlaps existing claim -> add evidence URL + excerpt Else -> PENDING claim (UNKNOWN/ANALYSIS/SCENARIO) + evidence

Re-runs are idempotent via unique constraints on (event, statement) and (claim, url).

11. AI Analysis Pipeline

Pipeline Flow

Event metadata + linked claims/articles | v Versioned prompt (event-analysis-v1) | v Model call (HTTP if LLM_API_KEY set, otherwise deterministic stub) | v JSON parse -> Zod schema validation -> URL allowlist check | v Sanitization (strip extra fields, validate enums) | v analysis_runs row (audit) + DRAFT impact assessment | v Human review (M10) -> Publish

What Is Stored

FieldPurpose
analysis_runs.model_nameWhich model produced the JSON
analysis_runs.prompt_versionevent-analysis-v1 today
analysis_runs.input_referencesEvent, claim IDs, article IDs, allowed URLs
analysis_runs.outputValidated JSON after sanitization
impact_assessments.analysis_confidenceLOW / MEDIUM / HIGH (estimate)
impact_assessments.evidence_strengthComputed from linked evidence (not the model)

Safety Checks

  1. Schema validation (Zod): Extra fields stripped; wrong enums fail the run
  2. URL allowlist: Any http(s) URL not in the input allowlist fails the run
  3. Claim type: Model claims are stored PENDING and never as FACT
  4. Confidence: analysisConfidence cannot be a percentage
  5. UNKNOWN is valid: If evidence is thin, UNKNOWN / LOW confidence is correct

Failure Modes

14. Impact Chains

What Is an Impact Chain?

An impact chain is a causal pathway showing how a global event leads to India-facing consequences:

Hormuz disruption (ROOT) | v Shipping disruption (CHANNEL) | v Oil transportation risk (CHANNEL) | v Higher energy costs (CHANNEL) | v India's import bill (IMPACT) | v Inflation pressure (IMPACT) | v Rupee / monetary policy (IMPACT)

Data Model

TablePurpose
impact_chainsVersioned chain container (v1, v2, ...)
impact_chain_nodesNodes with key, kind (ROOT/CHANNEL/IMPACT), label, description
impact_chain_edgesDirected edges (from_key -> to_key)

Graph Validity Rules

  • Exactly one ROOT node
  • No cycles (acyclic graph)
  • All nodes reachable from root
  • Enforced by validateChainGraph in @bharatlens/shared

Lifecycle

  1. AI proposes a DRAFT chain (prompt v2)
  2. Reviewer edits in admin console
  3. Reviewer publishes (freezes version)
  4. events.current_impact_chain_id updated
  5. Published versions are immutable history

Rendering

The public event page renders the current chain as a top-down stepper, layered client-side from the graph using a longest-path DAG layering algorithm. No per-event hardcoding.

16. Search System

Implementation

Search uses PostgreSQL full-text search with a stored generated tsvector:

  • events.search_vector - generated column, english configuration
  • Weighted: A=title, B=summary, C=description
  • Queries use websearch_to_tsquery matching
  • ILIKE fallback for partial words
  • Results ranked by ts_rank when sort=relevance

Search Endpoint

GET /api/v1/search?q=india+oil&sort=relevance

Why Not Elasticsearch?

  • Volume is tiny (hundreds of events, not millions)
  • PostgreSQL FTS is sufficient for this scale
  • Adding Elasticsearch introduces operational complexity
  • Can evaluate later when actual requirements justify it

22. AI Evaluation Harness

Overview

The evaluation harness (M15) validates AI behavior against fixtures. It does NOT use model-emitted percentages as accuracy scores.

Two Tiers

1. Offline (runs in normal test suite)

  • Adversarial output corpus pushed through parse -> validate -> sanitize
  • Proves schema enforcement, FACT stripping, URL-fabrication rejection
  • No network calls required

2. Live Scenarios

  • 6 gold-labeled fixtures
  • Scored on behavioral counts:
    • Schema pass rate
    • Raw FACT leaks
    • Fabrication caught
    • Chain validity
    • Overall-level exact vs adjacent-rank agreement
    • Dominant claim-type agreement
  • Results compared against committed baseline.json
  • --check flag fails on any dropped metric

Commands

# Run evaluation with deterministic stub
pnpm eval:ai --model=stub

# Run with live LLM
pnpm eval:ai --model=live

# Check against baseline (CI mode)
pnpm eval:ai --check

# Update baseline after intentional changes
pnpm eval:ai --update-baseline

Key Principles

  • Levels are never merged into a score
  • Model-emitted confidence is never treated as accuracy
  • Baseline updates are deliberate commits alongside prompt/stub changes
  • Fixtures are gold-labeled by human review

23. Design Principles

Simplicity First

  • Prefer the simplest architecture that solves the current problem
  • No premature microservices, Kafka, Elasticsearch, or Kubernetes
  • PostgreSQL is sufficient for search at current scale
  • Redis is used only when it solves a real problem

Evidence-First Architecture

  • Never trust raw LLM output
  • Claims backed by sources, not just model output
  • Separate evidence_strength from analysis_confidence
  • FACT claims require human review
  • UNKNOWN is a valid result (preferred over hallucination)

Political Neutrality

  • No promotion of political parties or ideologies
  • No portrayal of countries as inherently good or bad
  • No inflammatory language or nationalist propaganda
  • Source transparency over manufactured confidence

Source Transparency

  • Every important claim has supporting sources
  • Never fabricate URLs, quotes, statistics, or sources
  • Store metadata, not full copyrighted articles
  • Respect robots.txt and API terms

AI Safety

  • Never fabricate events, sources, quotes, or statistics
  • Never present speculation as fact
  • Never claim certainty without evidence
  • Prefer "insufficient evidence" over hallucinating
  • Every AI output is auditable (model, prompt version, sources, review status)

Append-Only History

  • Impact assessments are versioned (v1, v2, v3...)
  • Corrections create new versions, never overwrite
  • Event updates form a timeline
  • Analysis runs are an audit trail
  • Published versions are immutable

Human-in-the-Loop

  • AI generates drafts; never auto-publishes
  • Humans review claims, assessments, and chains
  • Admin console provides full inspection tools
  • Public API only shows approved/published data

Fail Fast

  • Missing required env vars crash on boot
  • Invalid config is caught at startup
  • Zod validates all AI output
  • Unique constraints prevent duplicate data
